## P0. Безопасность — сделать до всего остального

### 1. Path traversal: доступ к токену и всем данным

**Подтверждено на рабочем сервере** (`curl --path-as-is`, тело не выводил, чтобы не светить токен):

| Запрос | Ответ | Что происходит |
|---|---|---|
| `GET /data/config.json` | `404` | защита срабатывает |
| `GET /./data/config.json` | `200` | отдаётся `config.json` с MCP-токеном |
| `GET /%2e/data/config.json` | `200` | то же самое через URL-кодирование |
| `GET /docs/../data/config.json` | `200` | обход через `..` |
| `GET /./data/doc.json` | `200` | все заметки, доски, настройки |
| `GET /./server.py` | `200` | исходный код сервера |
| `GET /./tools/fetch_fonts.py` | `200` | служебные скрипты |
| `HEAD /data/config.json` | `200` | `do_HEAD` не проверяет путь вообще |
| `HEAD /./data/config.json` | `200` | то же самое

Причина в `server.py`:

```python
# server.py, ~1554
segments = [s for s in path.split("/") if s]
if segments and segments[0] in {"data", ".git", ".opencode", "tools", "__pycache__"}:
    self._send_text(404, "Not found")
    return
...
super().do_GET()
```

Проверка смотрит только на **первый сырой сегмент** пути. `SimpleHTTPRequestHandler` внутри `translate_path()` сам выполняет `unquote()` и `posixpath.normpath()`, поэтому `/./data/...` превращается в `/data/...` уже **после** проверки. `do_HEAD` вообще вызывает `super().do_HEAD()` без всякой проверки.

**Почему это критично:** сервер по умолчанию слушает `0.0.0.0` (`server.py:1736`), то есть доступен не только с этого компьютера, но и с любого устройства в той же Wi-Fi/LAN. Через украденный токен можно читать и менять все данные через `/api/doc` и MCP. Пароль фактически лежит в открытом виде по адресу `/./data/config.json`.

**Минимальное исправление:**

1. Нормализовать путь **до** проверки, а не после:
   ```python
   import posixpath
   raw = unquote(urlparse(self.path).path).replace("\\", "/")
   norm = posixpath.normpath(raw)
   parts = [p for p in norm.split("/") if p]
   ```
2. Запрещать `data`, `.git`, `.opencode`, `tools`, `__pycache__` и любые скрытые сегменты **на любой позиции**, а не только первым.
3. Запрещать `*.py`, `*.bat`, `*.cmd`, `*.ps1`, `*.tmp`, `*.log`, `*.db` в любом сегменте.
4. Дополнительно проверять физический путь:
   ```python
   target = (ROOT / Path(*parts)).resolve()
   if target != ROOT and ROOT not in target.parents:
       return 404
   ```
5. Применить ту же проверку в `do_HEAD` и, лучше, вынести в общий `_static_allowed(path)`.
6. Отключить листинг каталогов: переопределить `list_directory()` и отдавать `404`.
7. **После патча сменить токен** в `data/config.json` (удалить поле `token` и перезапустить сервер либо записать новый случайный) и перезапустить сервер.
8. Пока патч не применён, не оставлять сервер запущенным в общей сети. Если телефон не нужен, запускать с `--host 127.0.0.1`.

### 2. CORS `*` на всех ответах

`server.py:1407-1412` добавляет:

```python
self.send_header("Access-Control-Allow-Origin", "*")
```

...ко всем ответам, включая `/api/doc` и статику. В сочетании с утечкой токена это позволяет любому сайту, открытому в браузере, прочитать данные с локального сервера (в браузерах/сетях, где не блокируется public→private). Даже без токена это лишняя поверхность атаки.

Что сделать:

- убрать `Access-Control-Allow-Origin: *`;
- для приложения, открытого с того же origin, CORS не нужен вообще;
- если нужен доступ с другого origin — разрешать только явный список origins из конфига;
- не отправлять CORS-заголовки для статики;
- замаскировать `?token=` в логах (`log_message` сейчас маскирует только `/mcp/<token>`, но не query-параметр).

### 3. XSS через импорт и синхронизацию

`U.sanitizeHtml()` вызывается при добавлении/редактировании заметки (`model.js:542, 559`; `panels.js:265`; `board.js:1012`), но **не при загрузке документа**. В `normalizeDoc()`:

```js
// model.js:317
note.html = typeof note.html === "string" ? note.html : "";
```

Импорт (`tools.js:483`) и синхронизация (`sync.js:281`) проходят через `normalizeDoc()`, то есть HTML попадает в документ как есть. Дальше:

```js
// panels.js:623
dContent.innerHTML = n.html || "";

// board.js:103
body.innerHTML = n.html || "";
```

Файл `.probka` с `<img src=x onerror=...>` выполнит код при открытии заметки. Это уже не «теоретический» XSS, а последствие обычного импорта чужого файла.

Что сделать:

- в `normalizeDoc()`: `note.html = U.sanitizeHtml(note.html);`
- в местах рендера оставить санитизацию как второй рубеж (или гарантировать, что в DOM попадает только очищенный HTML);
- проверять `url`/`source` и разрешать только `http:`, `https:`, `mailto:`, а не `javascript:`;
- добавить тест: импорт `<img src=x onerror=alert(1)>` не должен выполнять `alert`;
- не забыть про старые резервные копии и документ на сервере: после исправления они тоже должны проходить очистку при загрузке.

### 4. Заголовки безопасности и мелочи сервера

Добавить в `end_headers()`:

```text
Content-Security-Policy: default-src 'self'; script-src 'self';
  style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:;
  font-src 'self'; connect-src 'self' http: https:;
  object-src 'none'; base-uri 'none'; frame-ancestors 'none'
X-Frame-Options: DENY
Permissions-Policy: geolocation=(), microphone=(), camera=()
```

`style-src 'unsafe-inline'` пока нужен из-за inline-стилей, `connect-src http: https:` — из-за настраиваемого адреса синхронизации. После стабилизации CSP можно сузить.

Ещё:

- в `log_message()` маскировать `token=...` в query;
- ограничить число неудачных попыток авторизации (простой счётчик по IP с задержкой);
- не отдавать `server.py`, `docs/*.md` и служебные файлы без необходимости; статику лучше ограничить явным whitelist: `index.html`, `css/`, `js/`, `assets/`, `manifest.webmanifest`, `sw.js`, `docs/MCP.md` (если нужен).
- добавить в README предупреждение: «сервер с токеном не выставлять в интернет без HTTPS и VPN».

## P1. Сохранность данных и синхронизация

### 1. Синхронизация «залипает» после неудачной отправки

В `sync.js`:

```js
// schedulePush()
this._dirty = true;
...
// poll()
if (this._pushTimer || this._dirty) return;
...
// push(), catch
this._status = ...;
this._message = ...;
return false;          // _dirty остаётся true
```

Если `PUT /api/doc` не прошёл (ноутбук уснул, Wi-Fi моргнул, сервер перезапускался), `_dirty` остаётся `true`. Событие `online` вызывает только `poll()`, а `poll()` сразу выходит из-за `_dirty`. В итоге изменения не отправляются и чужие изменения не приходят, пока пользователь снова что-нибудь не изменит. Это тихая деградация, которую легко не заметить.

Что сделать:

- retry с экспоненциальной задержкой (5 с → 15 с → 60 с, максимум 5 минут);
- на `online` и `visibilitychange` сначала пытаться `push()`, если `_dirty`, и только потом `poll()`;
- после успешного push очищать `_dirty`;
- показывать в интерфейсе «есть неотправленные изменения» и кнопку «Повторить»;
- хранить очередь хотя бы в памяти и не терять её при переключении вкладки.

### 2. «Скачать с сервера» без подтверждения и backup

`sync.js:438-445` вызывает `pullNow()` сразу по клику. `pullNow()` делает `check()` + `poll(true)`, а `applyRemote()` заменяет `TB.model.doc` целиком, очищает историю undo и сразу сохраняет документ. Если на сервере пустой/старый документ, локальные данные исчезают без вопроса.

Что сделать:

- перед загрузкой показывать подтверждение: ревизия, количество записей, дата обновления;
- автоматически создавать backup с причиной «перед загрузкой с сервера»;
- после загрузки показывать тост «Загружено N записей, можно отменить»;
- ещё лучше — не заменять, а показать diff/выбор «оставить локальные / взять серверные / объединить».

### 3. Слияние «последний победил» теряет поля

`merge_docs()` (`server.py:267-350`) выбирает заметку целиком по `updated`. Если на телефоне изменить дедлайн, а на компьютере — текст той же заметки, одно из изменений будет потеряно. `baseRevision` клиент отправляет (`sync.js:240`), но сервер его не использует.

Для личного приложения это допустимо как временное решение, но пользователь должен понимать риск. Минимально:

- возвращать в ответе `conflict: true`, если ревизии разошлись;
- показывать предупреждение и делать backup перед применением;
- хранить `updatedBy`/`deviceId` и последнюю ревизию заметки;
- в перспективе — merge по полям или CRDT/журнал операций (это уже отдельный проект).

### 4. Резервные копии только «перед риском»

`store.createBackup()` вызывается вручную и перед импортом/восстановлением, но не регулярно. Нет ежедневной копии, нет копии перед `pullNow`, нет контроля размера.

Что сделать:

- авто-backup раз в сутки при первом запуске (или раз в 24 часа) с retention 8–14 штук;
- backup перед любым массовым изменением: импорт, загрузка с сервера, восстановление;
- показывать в настройках дату последней копии и размер хранилища;
- добавить `navigator.storage.persist()` и предупреждение при заполнении квоты > 80%;
- `writeFallback()` сейчас молча игнорирует переполнение localStorage (`store.js:75-79`) — стоит хотя бы один раз показать предупреждение.

### 5. Экспорт больших вложений ест память

`tools.js:412-448` собирает до 80 МБ вложений в base64 и делает `JSON.stringify` всего payload. На телефоне это легко даёт OOM; файлы >12 МБ молча пропускаются. Это не срочно, но неприятно.

Что сделать:

- экспорт в ZIP (локально через File System Access API на десктопе или серверный `/api/export.zip` с `zipfile` и потоковой отдачей);
- для офлайн-режима — JSON без вложений + отдельная папка/архив;
- ограничение на размер импорта и проверка структуры (защита от «zip bomb» и огромного JSON);
- показывать список пропущенных файлов, а не только счётчик.

## P2. Производительность и архитектура

### 1. Список задач не масштабируется

Замер на копии: 22 записи — «Задачи» ~37 мс; после добавления 1000 записей — **~896 мс** (`today` ~36 мс, `calendar` ~45 мс). Причина: `renderTasks()` каждый раз строит DOM для всех строк, а `U.titleOfNote()` и `U.plainText()` заново парсят HTML через `<template>` для каждой записи. На слабом телефоне 1000+ записей дадут заметные лаги.

Что сделать (по возрастанию сложности):

1. Кэшировать `title` и `plainText` по `note.id + note.updated` в памяти; сбрасывать при изменении `html`.
2. Ограничить список: «Показать ещё 100» вместо всех сразу.
3. Виртуализировать список (рендерить только видимые строки) — лучший вариант для 1000+.
4. Для поиска — debounce 150–250 мс и индекс по словам, а не полный перебор с парсингом на каждый ввод.
5. Для календаря — не перестраивать всю сетку при смене месяца, обновлять только ячейки.

### 2. Undo хранит 60 полных копий документа

`model.js:972-976`:

```js
this.history.push(JSON.stringify(this.doc));
if (this.history.length > 60) this.history.shift();
```

Сейчас документ ~21 КБ, то есть ~1,2 МБ — нормально. Но с ростом до 1 МБ это уже ~60 МБ строк в памяти, плюс `redoStack`. На телефоне это опасная зона.

Что сделать:

- ограничивать историю не количеством, а байтами (например, 5–10 МБ);
- хранить не весь документ, а обратные патчи/команды (сложнее) или хотя бы снимки только изменённых сущностей;
- объединять быстрые изменения в один снимок (сейчас в редакторе контента это уже сделано через `contentDirty`, но не во всех полях);
- не делать снимок на каждое движение стикера — для drag использовать `silentUndo` и один снимок на завершение жеста.

### 3. Каждое сохранение пишет весь документ дважды

`saveSoon()` держит debounce 420 мс, затем `store.saveDoc()` пишет объект в IndexedDB и **полную JSON-строку** в localStorage (`store.js:105-110`). Для 20 КБ это незаметно, для большого документа — лишняя работа и риск квоты.

Что сделать:

- localStorage-зеркало писать реже (например, раз в 30–60 с или только при закрытии), а не на каждое изменение;
- при превышении лимита не пытаться писать полный документ, а хранить «грязный» флаг и последнюю успешную копию;
- добавить `schemaVersion` и функцию миграций. Сейчас `doc.version = 1` жёстко задан в `normalizeDoc()` (`model.js:267`), но механизма миграций нет. Однажды это станет больно.

### 4. Таймер фокуса врёт в фоне

`main.js:151-159`:

```js
focus.left -= 1;
```

`setInterval` в фоновой вкладке тротлится, а при сне компьютера просто останавливается. Через 25 минут в фоне таймер может показать 24:17. Кроме того, состояние таймера теряется при перезагрузке.

Что сделать:

- хранить `startedAt` и считать `left = total - floor((Date.now() - startedAt) / 1000)`;
- пересчитывать при `visibilitychange` и `focus`;
- сохранять состояние в `localStorage`/`doc.settings.focus`, при запуске предлагать «продолжить»;
- добавить секундомер (считает вверх) и обратный отсчёт (то же, но без Pomodoro-логики) — это прямо просит ТЗ.

### 5. Документ и рендер — не повод для немедленного рефакторинга

Архитектура «один документ + полный рендер» нормальна для личного приложения на 1–3 тысячи записей, если добавить виртуализацию и кэш. Переписывать всё на нормализованные таблицы/React не нужно: это усложнит офлайн-режим и MCP. Лучше точечно усилить текущую модель.

## P2. Продуктовые улучшения

### 1. Человеческие даты в быстром захвате

Сейчас форма использует `datetime-local`, а ТЗ прямо просит «завтра», «в пн». Это одна из самых заметных недостающих функций.

Идея: функция `parseHumanDate(text, now)` с поддержкой:

- `сегодня`, `завтра`, `послезавтра`;
- `в пн`, `в понедельник`, `в следующий вторник`;
- `через 3 дня`, `через неделю`, `через месяц`;
- `20 окт`, `20.10`, `20 октября`, `20.10.2027`;
- `18:00`, `в 18`, `к 9 утра`;
- `каждый день`, `каждую пятницу` (для `repeat`).

Показывать разобранный результат до сохранения: «Завтра, 18:00 · срок». Если неоднозначно — предлагать выбор. Это же можно использовать в поле «Срок» карточки, а не только в capture.

Польза: меньше кликов, меньше «потом разберу». Сложность: 1–2 дня + тесты.

### 2. Неделя и time-blocking

Сейчас календарь только месячный, а встречи — это заметки с `due`. В ТЗ есть недельная сетка и перетаскивание задачи в время.

Идея:

- добавить `meta.start`/`meta.end` (локальное время) и режим «Неделя»;
- встреча занимает блок, дедлайн — маркер;
- перетаскивание задачи в сетку создаёт блок и при необходимости ставит `due`;
- на «Сегодня» показывать «Сейчас: …» и «Дальше: …» с обратным отсчётом;
- предупреждать о накладках.

Это большая фича (4–6 дней), но именно она превращает «список дел» в «план дня».

### 3. Блок текущего контекста

В ТЗ есть «переключатель приоритетной сферы по времени суток». Простое решение:

- в настройках задать интервалы: работа 09:00–18:00, учёба 18:00–22:00, личное — остальное;
- на «Сегодня» сверху показывать «Сейчас: Работа» и 2–3 задачи/шаблона из этой сферы;
- кнопка «сменить контекст» на 1 час.

Польза: экран сам подсказывает, чем заняться, без нового раздела. Сложность: 2–4 часа.

### 4. Работа: «Быстрые ответы» и «Инструкции»

База шаблонов уже умеет поиск, копирование, избранное и счётчик. Не хватает разделения на два раздела и сценария «нет решения → задача дописать шаблон».

Идея:

- добавить `meta.section` (`quick`/`guide`) или тег `#инструкция`;
- сверху — два таба и поиск;
- у шаблона — кнопка «Не подошло? Создать задачу дописать»;
- сортировать избранное выше, показывать топ-5 по `usage`;
- добавить горячую клавишу «Копировать» на карточке (например, `Ctrl+C` при фокусе, без выделения текста).

Сложность: 1 день.

### 5. Учёба: реальные статусы ДЗ

Сейчас ДЗ — это задача с общим `status`: inbox/today/doing/done. В ТЗ нужны «не начато / в работе / сдано / проверено». Это важно, потому что «сдано» и «проверено» — разные состояния, и по ним видно долги.

Идея:

- `meta.hwStatus`: `todo` / `doing` / `submitted` / `checked`;
- на карточке предмета — счётчики и просрочки;
- «сдано» не считается полностью закрытым, пока не «проверено» (или отдельный флаг);
- напоминание «проверить, что ДЗ приняли» через 2 дня после сдачи.

Сложность: 1–2 дня.

### 6. Проекты: «идея → задача», а не «идея → проект»

Сейчас кнопка «В проект» (`views-life.js:569-572`) превращает саму идею в проект, меняя `kind` на `project`. Это теряет исходную формулировку идеи и не соответствует ТЗ, где идея должна «стать задачей» и попасть в роадмап.

Идея:

- кнопка «В задачу» создаёт новую задачу с `projectId` и `meta.roadmap`, а идее ставит `stage = roadmap`;
- отдельная кнопка «Создать проект» — только если идея действительно про новый проект;
- канбан «Сейчас / Дальше / Потом / Готово» с drag&drop и WIP-лимитом;
- журнал релизов уже есть, добавить связь «релиз → задачи».

Сложность: 1–2 дня.

### 7. Обзор: проводник из 6 шагов

Сейчас «Обзор» — это набор секций. ТЗ просит проводник. Идея:

1. Разобрать входящие.
2. Просроченное: перенести/закрыть/удалить.
3. Дедлайны на 2 недели.
4. Цели недели (текст + 3 задачи).
5. Идеи: в задачу / отклонить / оставить.
6. Итоги: что получилось, что переносится, что мешает.

Сверху — прогресс «3 из 6», кнопка «Дальше», возможность прервать и вернуться. В конце — автосохранение в `settings.weeklyGoals` и запись в журнал. Сложность: 1–2 дня.

### 8. Аналитика, которой не хватает

Сейчас `stats()` (`model.js:955-968`) считает сделанные, просроченные, фокус по сферам и топ-5 шаблонов. Полезно добавить:

- динамику по неделям: сделано / просрочено / перенесено;
- точность оценок: `estimate` против `focusMinutes` у завершённых задач;
- «что переносится чаще двух раз» — список кандидатов на удаление/декомпозицию;
- время по сферам с долей и трендом к прошлой неделе;
- топ шаблонов не 5, а 10, с кнопкой «копировать» прямо в аналитике;
- простые inline-SVG-графики, без библиотек.

Важно: `postponed` сейчас считает активные заметки с `postponedCount > 0` и `updated` в окне, а не фактические переносы. Для честной аналитики нужен журнал событий (`noteId`, `type`, `at`, `from`, `to`) или хотя бы `postponedAt[]`.

### 9. Фоновые напоминания: Telegram-бот или Web Push

Главное ограничение PWA: напоминания работают, только пока приложение открыто. В README это честно написано. Но у проекта уже есть Python-сервер и MCP — грех не использовать его для фоновых уведомлений.

Самый практичный вариант — **Telegram-бот**:

- токен бота и `chat_id` в `data/config.json`;
- long polling через `urllib` (без новых зависимостей);
- команды `/today`, `/add купить хлеб завтра`, `/done <id>`, `/digest`;
- утренний дайджест в 08:00 и напоминания о дедлайнах, даже если PWA закрыта;
- кнопки «Готово», «+1 день», «Открыть»;
- allowlist по `chat_id`, чтобы бот не стал публичным.

Альтернатива — Web Push (VAPID + шифрование), но это сложнее и требует HTTPS. Telegram даст 80% пользы за 2–3 дня.

### 10. Захват с Android и Windows

- **Android:** добавить в `manifest.webmanifest` `share_target` (`action: "/share-target"`, `method: "POST"`, `enctype: "multipart/form-data"`), в `sw.js` принимать POST, складывать текст в IndexedDB как «pending capture», а приложение при следующем открытии показывает «Поймано из другого приложения». Это одна из самых полезных фич для «второго мозга».
- **Windows:** глобальный хоткей из браузера недоступен. Варианты: PWA-шорткат (уже есть), небольшой AutoHotkey-скрипт, либо обёртка Tauri/WebView2. Не начинать с обёртки: сначала share_target и быстрый capture.
- **Share из других приложений на десктопе:** можно добавить `file_handlers` для `.probka` и `protocol_handlers` для `web+probka`, но это уже nice-to-have.

Отдельное важное ограничение: **на Android по адресу `http://192.168.x.x:8765/` service worker не регистрируется**, потому что это не secure context. Без service worker не будет полноценной офлайн-работы и установки PWA; `share_target` тоже требует HTTPS. README стоит уточнить: для телефона нужен HTTPS-туннель (Cloudflare Tunnel, ngrok и т.п.) или `adb reverse`/localhost, а LAN-HTTP годится только как временный доступ к данным. На Windows `http://localhost` — исключение, поэтому там PWA работает.

### 11. Свайпы и мобильные действия

На мобильном сейчас действия — кнопки в строке задачи. ТЗ просит свайпы. Идея:

- свайп вправо — «Готово»;
- свайп влево — «+1 день» / «В архив» (два порога);
- после действия — тост с «Отменить» на 5 секунд;
- не конфликтовать с горизонтальным скроллом и панорамой доски: свайпы только на строках задач, не на стикерах.

Сложность: 1–2 дня.

### 12. Мелочи, которые заметны

- **Горячие клавиши:** в `overlays.js:524-536` обещаны `N`, `Ctrl+S`, `Space`, но обработчиков нет (`main.js:291-334`). Либо реализовать: `N` — новая запись/захват, `Ctrl+S` — `saveNow()`, `Space` — панорама доски без ввода; либо убрать из подсказки.
- **Повторение месяца:** `nextDue()` (`model.js:359-370`) использует `setMonth(+1)`. 31 января → 3 марта, 29 февраля → 1 марта. Нужно ограничивать последним днём месяца.
- **Inbox → done → today:** `setStatus()` (`model.js:653`) при снятии `done` ставит `today`, даже если запись была во входящих. Лучше возвращать предыдущий статус.
- **Тема:** есть только ручная светлая/тёмная. Добавить «как в системе» через `prefers-color-scheme`.
- **Обновление PWA:** нет уведомления «доступна новая версия». Добавить обработку `updatefound`/`controllerchange` и кнопку «Обновить».
- **Печать:** `@media print` уже есть. Добавить кнопку «Печать дня/недели» — дешёвый и полезный сценарий.
- **Экспорт в календарь:** генерация `.ics` для дедлайнов и встреч, чтобы подписываться в Google Calendar/Outlook. 1 день.
- **Поиск:** сейчас подстрочный, без фильтров по архиву/типу/сфере. Добавить чипы и команды «создать задачу …», «открыть работу», «экспорт».

## P3. Качество кода и процессы

### 1. Тесты

Тестов нет вообще. Для проекта без сборки это можно сделать без Node:

- `tests/test_server.py` на `unittest`: path traversal, HEAD, CORS, авторизация, merge, tombstones, MCP tools;

- `/data/config.json`, `/./data/config.json`, `/%2e/data/config.json`, `/docs/../data/config.json`, `HEAD` — все 404;

- после неудачного push и восстановления сети синхронизация сама догоняет;
- `pullNow` создаёт backup и требует подтверждения;
- таймер в фоне совпадает с реальным временем;
- 1000 задач рендерятся меньше 100 мс (после виртуализации);
- 31 января + месяц = 28/29 февраля.
